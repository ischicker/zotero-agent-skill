# Gotchas

Read this when something fails or looks odd.

- Library id (`L21`), group id (`6713340`), collection key (`GLCG2D2J`) and connector collection id (`C288`) differ; the script maps names to all of them. Collection names must be unique within a library (an allowlist entry whose name matches 0 or 2+ collections is ignored, with a warning).
- Local-API writes need `Zotero-Server-ID` (any response header) and a single-use `Zotero-API-Key` from `POST /api/local/authorize`; more than 5 dialog-triggering requests a minute get 429.
- "Always Allow" in that dialog creates a key that never expires, stored in plain text in `localAPIKeys.json` in the Zotero profile directory and accepted from any program. The script warns when Zotero reports such a key (`"remember": true`) and does not reuse it. To revoke: quit Zotero (it caches the file), remove the entries with `"remember": true`, restart.
- `write refused: no allowlist file ...` / `... is not in the allowlist`: the user has to create or extend the file; `allowlist` shows the path and what it allows. The library root is never a target, so `attach --new` needs `--coll`.
- `import refused: --confirm ... does not match`: the spec, the verify output, the flags or the library changed since `plan` (e.g. an item was added meanwhile, so dedupe differs). Run `plan` again with the same flags and get the user's approval for the new hash. `plan` and `import` must get the same `--allow-unverified`, `--pdf`, `--allow-spec-pdf` and `--max-pdf-mb`.
- `organize --confirm` covers item versions too: any edit to one of those items in Zotero after the dry run (even by the user) invalidates the hash.
- After `organize`, papers live in subcollections: any lookup must search the parent and its subcollections (the script does; ad-hoc scripts must too). A batch write whose objects are all unchanged returns `unchanged`, not `successful`, and still costs a dialog: check the payload before writing.
- The connector does not dedupe; the script does (DOI/arXiv ID, title for unverified, fuzzy text for notes). Trashed items do not count.
- The connector's `saveItems` saves into the collection currently selected in the Zotero window; `updateSession` then moves the items to the allowlisted target. If the run dies between the two calls, the items stay where the user's selection was. The script checks the target before `saveItems`, but cannot control that intermediate step.
- Crossref 429s under bursts (script backs off); arXiv asks for ~3 s between calls and the script does not wait, so a long run of arXiv IDs can be throttled; some publisher/ISLS PDFs 403 scripts, so list them for manual download.
- PDFs are off unless `--pdf`. With it, a candidate on plain http, on a private address or redirecting there is refused, and a PDF over the cap is skipped without being read in full. A spec's own `pdf` URL needs `--allow-spec-pdf`.
- `organize` waits 3 min per approval dialog. If nobody clicks Allow it stops with `NOT applied` (item batch) or `NOT created` (subcollections); batches already approved stay applied. Run `organize --dry-run` again: it works from the library's current state and skips items already correct (a dry run on three already-organized specs showed 0 changes), and prints the new hash.
- `attach --item` makes the (empty) attachment item before the upload. If the upload or registration then fails or is denied, that empty attachment stays under the parent; the error names its key (`trash LIB KEY`). A file already attached is not detected: attaching the same PDF twice makes two attachments. `attach refused: ... not inside any attach_dirs entry`: move the file into an allowed directory (symlinks pointing elsewhere do not count).
- `write refused: cannot append to the write log`: the log directory under the home directory is not writable; writes are refused rather than sent unlogged.
