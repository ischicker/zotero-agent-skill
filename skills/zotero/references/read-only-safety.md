# Why the read-only commands are read-only, and what bounds the writes

`SKILL.md` lists the commands pre-approved in `allowed-tools` (`status`, `libs`, `colls`, `ls`, `find`, `notes`, `path`, `plan`, `where`, `allowlist`, `log`, `export`, `bundle`, `selftest`) and states that they only issue HTTP GET to Zotero on loopback and create, modify or delete nothing. This page is the argument for that, so it can be checked rather than trusted. It also covers `verify`, which is pre-approved with a wider but still bounded guard, and the checks every write command goes through (see the end).

This safety is defended in depth:

1. *Zotero's own docs.* The Local API page states reads need no authentication and that "write requests (Zotero 10+) require a local API key" the user grants in a Zotero confirmation dialog: <https://www.zotero.org/support/dev/web_api/v3/local_api>. Writes use POST/PUT/PATCH/DELETE (<https://www.zotero.org/support/dev/web_api/v3/write_requests>); GET is a *safe* method, i.e. read-only by definition (RFC 9110 section 9.2.1: <https://httpwg.org/specs/rfc9110.html#safe.methods>). So even a buggy GET cannot change the library: Zotero would reject a write without a key that the user approved.
2. *The host is loopback.* `HOST` comes from `ZOTERO_HOST` (default `http://127.0.0.1:23119`), and the guard below trusts every URL under `HOST`. So `canonical_host()` refuses to start unless the value is `http://` plus `127.0.0.1`, `[::1]` or `localhost`, an explicit port and nothing else (no userinfo, path, query or fragment); `localhost` is rewritten to `127.0.0.1` so a hosts-file entry cannot redirect it. `selftest` prints a `host:` line for remote hosts, lookalikes (`127.0.0.1.evil.example`), userinfo tricks on both sides of the `@`, https, a missing port, a path and the `127.1` short form.
3. *The script's runtime guard.* Before any read-only command runs, `http()` in `scripts/zotero.py` is given `GUARD = LOCAL_ONLY`; any non-GET or off-host request (including a redirect to one) exits with "BUG: read-only command attempted ...". Prove it without Zotero: `python3 -I ${CLAUDE_SKILL_DIR}/scripts/zotero.py selftest` (every write verb and off-host URL must print `BLOCKED ok`).
4. *Reading the code.* Only `local_write()` (dialog-gated), `connector()` (import path) and the two file-upload POSTs in `attach_existing()` can write. `grep -n "connector(\|local_write(\|method=\"POST\"" scripts/zotero.py` shows every call site; none is reachable from the commands above (`cmd_plan` calls `build_import()`, `describe()` and `organize(dry=True)`, which reach only `zget()`; `organize` sends nothing when `dry` is true). `allowlist` and `log` only read their own file (and `allowlist` the collection list, via GET). `export` reads with GET (`.../collections/<KEY>/items/top`, and `.../items?format=bibtex&itemKey=...`, which runs Zotero's BibTeX translator server-side) and writes only to stdout, or with `--out` to a file it creates with mode `x` (never an existing path) and only with the extension of the chosen format; `selftest` has `export:` lines for both rules. `bundle` reads with the same GETs as `export` plus `.../items/<KEY>/children` and `.../items/<KEY>/file/view/url` (like `path`), so it runs under `LOCAL_ONLY` too. It writes local files only: copies and `manifest.csv`, each opened with mode `x`, in a folder that must be new or empty and strictly inside an `export_dirs` entry of the user's allowlist file, compared after resolving `..` and symlinks and checked again after the folder is created (`bundle_dir_problem()`). It copies only files whose resolved path is `.../storage/<attachment key>/<name>` and that start with `%PDF-` (`storage_file_problem()`), so a linked-file attachment cannot make it copy an arbitrary file into a folder meant for upload. File names are built from the 8-character item key (checked) and an ASCII-only surname and year. `selftest`: `bundle:` lines.

## `verify`

`verify` is pre-approved but is not read-only: it resolves identifiers over the network and writes one file. Its bounds are the same kind of checkable claim:

1. *Network.* Before `verify` runs, `GUARD` is set to `REMOTE_READ`: GET only, and only to Zotero on loopback, `https://api.crossref.org/`, `https://export.arxiv.org/` and `https://api.openalex.org/`. Redirects are re-checked (`_GuardedRedirect`). `selftest` prints a `BLOCKED ok` line for a POST, another host, a look-alike host, a `user@host` trick, plain http and an off-host redirect. The only data sent is the DOI/arXiv identifier, inside the URL. `verify` records open-access PDF candidates but downloads nothing, and it no longer lets the spec's free-form `pdf` URL replace them.
2. *Disk.* `verify` writes one file, at the path `resolved_for()` returns for the spec. That path is always inside `run_dir()`, which the script creates mode 0700 under the system temp dir and refuses to use if it is not a directory owned by the user. There is no option to choose the output path.
3. *Reading the code.* `cmd_verify` reaches the network only through `crossref()`, `arxiv()` and `pdf_candidates()` (OpenAlex), plus the version ping in `require_zotero10()`; it does not call `connector()` or `local_write()`.

## `resolve`

`resolve FILE` runs under the same `REMOTE_READ` guard as `verify` (it is in `VERIFY_CMDS`): GET only, to Crossref, arXiv, OpenAlex and Zotero on loopback, redirects re-checked. Unlike `verify` it sends a title, a first-author name and a year per entry (Crossref `query.bibliographic`, arXiv `ti:` search). It never fetches URLs found in its input (`hint_url`, publisher pages, PMC); `selftest` has `resolve:` lines showing those are blocked. Its one write is a proposal file at `proposal_for()`, inside `run_dir()`. It does not read or change the library, and it does not modify the input file.

## What bounds the write commands

`import`, `organize`, `note`, `attach` and `trash` are not pre-approved, so the user sees each command before it runs. Beyond that:

1. *Allowlist, two layers.* A JSON file owned by the user (`allowlist` prints its path; `~/AppData/Roaming/zotero-skill/config.json` on Windows, `~/Library/Application Support/zotero-skill/config.json` on macOS, `~/.config/zotero-skill/config.json` elsewhere; not read from environment variables) lists the collections writes may touch. Missing, unreadable or malformed (or, on POSIX, writable by others): nothing is allowed.
   - `local_write()` refuses, before any dialog, objects that touch an item outside the allowed collections (child items count by their parent), add or remove a membership outside them, create a collection outside an allowed tree (`"subcollections": true`), or change any existing collection (`scope_violations()`). `connector_scope()` checks the import/attach target and opens the one connector session the run may use.
   - Under both, `http()` refuses every non-GET request that no such check covered (`write_violation()`): libraries not checked, the authorize and upload endpoints before a check, connector calls from another session or to another target, connector endpoints the skill does not use, and anything off loopback.
   - `selftest` covers parsing, the object rules and the backstop (`allowlist:`, `scope:` and `backstop:` lines).
   - Selected collection: the connector's `saveItems` saves into the row selected in the Zotero window (`getSaveTarget()` in Zotero's `server_connector.js`) before `updateSession` moves the items. `connector_scope()` and, again, `connector()` right before every `saveItems` read that row with `getSelectedCollection` (`switchToReadableLibrary: true`, so it resolves the way `saveItems` does) and refuse unless it is an editable, allowlisted collection, compared by connector target id; an unreadable response is a refusal. `selftest`: `preflight:` lines.
   - Trash: an item is only trashed if every collection it is in (a child: its parent's) is allowlisted. `selftest`: `scope: trash` lines.
   - Filing in (`filing_only()`): the one write allowed on an item outside the allowlist is an object with only `key`, `version` and `collections` that keeps every existing membership and adds only allowlisted collections. Its only effect is inside an allowlisted collection. `selftest`: `scope: file` lines (adding with a tag change, dropping a membership, adding a non-allowlisted collection or adding nothing are refused).
2. *Plan hash.* `plan`, `organize --dry-run` and `note --dry-run` print the target and the allowlist file (path and SHA-256 of its bytes), then a SHA-256 over a canonical serialisation (sorted keys, no whitespace, UTF-8) of exactly what would be sent: target, item records with notes and tags, placement, PDF policy and URLs per item, and the allowlist fingerprint; or for organize, the exact objects with their versions plus the fingerprint. The write needs `--confirm HASH` and recomputes it; any change to the spec, the flags, the library state or the allowlist file is a mismatch. The refusal does not print the expected hash. `selftest`: `hash:`, `allowlist hash:` and `confirm:` lines.
3. *PDFs.* Nothing is downloaded without `--pdf`. With it, only https URLs to named or public hosts (no userinfo, loopback, private or link-local addresses), re-checked on every redirect, read up to the cap and no further, starting with `%PDF-`. The spec's `pdf` URL needs `--allow-spec-pdf`. `attach` only reads files inside `attach_dirs`, compared after resolving `..` and symlinks. `selftest`: `pdf:`, `pdf plan:` and `attach:` lines.
4. *Write log.* One JSON line per write request (time, command, library, collection, method, endpoint, number of objects, SHA-256 of the payload, HTTP status), never content; checked to be appendable before the request is sent. `log` prints it. `selftest`: `log:` lines.

What these checks do not do: they cannot stop a process with the user's file permissions from editing the allowlist file (in Claude Code, `Read`/`Edit` deny rules on its folder stop the file tools and file-naming shell commands, but not a script that opens it, and the OS sandbox is not available on native Windows), they do not make the connector show a dialog, and they cannot catch a selection change in Zotero between the preflight and `saveItems`. See `gotchas.md`.
